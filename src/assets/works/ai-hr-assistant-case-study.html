01Introduction

The AI HR Assistant is a conversational agent built around a realistic company scenario: Lashmi Exim and its 57-page Employee Handbook covering leave, probation, payroll, travel and reimbursements. Employees can ask questions in plain English and get answers that cite the relevant handbook chapter.

The interesting part is not that it chats. It is that it knows when not to let the LLM answer. Policy explanations come from retrieved handbook text. Anything that involves arithmetic, dates or a yes/no eligibility decision runs through plain Python functions that encode the handbook's rules.

My role

System design, graph orchestration, RAG pipeline, tool logic, prompt design and observability setup.

Type

Company project · internal HR assistant, built to run as a CLI app and in LangGraph Studio.

Focus

Reliable, auditable AI behavior for a domain where a wrong answer has real consequences.

02Problem Statement

HR teams answer the same questions repeatedly: How many casual leaves can I take in a row? When does my probation end? Is my reimbursement claim still valid? The answers exist in the handbook, but employees rarely read 57 pages, and HR spends time on lookups instead of people.

Why a plain chatbot is not enough

  • LLMs are unreliable at rules and math. "1.5 days per month for 7 months" or "90 days from 1 January" are exactly the kind of thing a model will occasionally get wrong, with total confidence.
  • Hallucinated policy is worse than no answer. An invented rule about notice periods or claim windows can mislead an employee into a bad decision.
  • Questions are not all the same shape. "What is the CL policy?" needs retrieval. "Can I take 4 days of CL?" needs a decision. "What's the weather?" needs a polite refusal. One prompt cannot serve all three well.
  • Handbooks have gaps. A good assistant should say "the handbook doesn't define this" instead of guessing.

03Proposed Solution

A router-first, hybrid architecture built as a LangGraph state machine. Every question is classified first, then sent down the path best suited to it.

policy_question

Retrieve, then answer

For "what is the rule" questions. Relevant handbook chunks are retrieved and the model answers using only that context.

hr_action

Call tools, never guess

For calculations and eligibility checks. The agent must call one of seven deterministic tools and base its answer on the result.

out_of_scope

Refuse cleanly

Anything unrelated gets a fixed message. No LLM call is made, so there is nothing to jailbreak and no tokens spent.

Key design idea: when a validation tool rejects a request, the graph detours through retrieval to fetch the handbook rule behind the rejection, then asks the model to explain why, and what the employee can do instead. The decision is deterministic; the explanation is grounded in the real policy text.

04System Architecture

The graph has six nodes and three conditional branch points. Solid lines are the normal flow; the dashed orange path is the rejection-explanation detour.

LLM step Deterministic step

Request lifecycle

  1. Route. The router LLM returns a validated RouteDecision (route + one-line reason) via structured output, and per-question state is reset.
  2. Branch. A conditional edge sends the question to retrieval, the tool-using agent, or the out-of-scope reply.
  3. Act. Policy questions get a grounded answer. Action questions loop between hr_agent and tools until the model has what it needs.
  4. Explain rejections. If any tool returns valid: false, the graph fetches the relevant handbook section once and the agent writes the explanation with tool-calling disabled.
  5. Trace. Each run is tagged and traced in LangSmith with a session id and model metadata.

05Technical Breakdown

Shared graph state

One small typed state travels through every node. messages uses LangGraph's add_messages reducer so the conversation accumulates; the other keys control routing.

class HRState(TypedDict, total=False):
    messages: Annotated[list[AnyMessage], add_messages]
    route: Route                # "policy_question" | "hr_action" | "out_of_scope"
    policy_context: str         # retrieved handbook text
    rejection_explained: bool   # guards against looping the detour

RAG pipeline

The handbook PDF is loaded with PyPDFLoader, split with RecursiveCharacterTextSplitter (1,000 characters, 150 overlap), embedded locally with all-MiniLM-L6-v2 sentence-transformers, and held in an in-memory vector store. The retriever returns the top 4 chunks. It is built once at startup and reused by every request.

Conditional routing

Three small functions in edges.py make every branching decision: which path a question takes, whether a tool result was a rejection, and where the shared retrieval node should send control next. Keeping them separate from the nodes makes the flow readable from the graph definition alone.

def after_hr_tools(state):
    # Did a validation tool reject the request since the last AI message?
    ...
    if rejected and not state.get("rejection_explained"):
        return "explain_rejection"   # detour via retrieve_policy
    return "hr_agent"

One node, two callers

retrieve_policy is reached from two places. From the router it searches with the user's question. After a rejection it appends the tool's rejection reason to the query, so the search targets the rule that caused the rejection rather than the original wording.

06Core Features

Routing

Intent-aware paths

The prompt teaches the router the difference between asking for a rule and asking about a specific request, with side-by-side examples.

Grounding

Handbook-only answers

The policy prompt forbids invented rules and requires the model to say so when the context does not contain the answer.

Accuracy

Deterministic calculations

Leave accrual, probation end dates, payroll deadlines and allowances are computed by code, never from model memory.

Validation

Rule-based eligibility

Leave and reimbursement requests are checked against notice periods, probation status, day limits and document requirements.

Explainability

Cited rejections

Every tool result carries a policy_reference such as "Chapter 7.2", and rejections are explained using the retrieved handbook text.

Honesty

Admits policy gaps

If the handbook is silent, the tool returns an "undefined" result and tells the user to confirm with HR instead of guessing.

Safety

Scoped refusals

Off-topic questions get a fixed reply without ever reaching the model.

Observability

LangSmith tracing

Named runs, tags and session metadata make every conversation inspectable step by step.

08Engineering Challenges

1. Telling "the rule" apart from "my request"

Problem: "How many consecutive CL days are allowed?" and "Can I take 4 days of casual leave in a row?" look almost identical but need different handling.
Solution: A router prompt built around a key distinction with paired examples, plus structured output so the model cannot return anything but one of three routes.

2. Explaining a rejection without looping forever

Problem: A rejected request should be explained with real policy text, but an agent that can call tools may keep retrying them.
Solution: A rejection_explained flag in state allows the detour exactly once. On the second visit the agent is bound with tool_choice="none", so it can only write the answer.

3. Retrieving the right rule after a rejection

Problem: The original question ("Can I take 5 days of EL?") is a poor search query for finding the probation rule.
Solution: The retrieval node concatenates the question with the tool's rejection reason before searching, so the query contains the language of the rule itself.

4. Gaps and ambiguity in the policy

Problem: The handbook says to claim within 15 days and that claims over 45 days need Finance Head approval, but says nothing about days 16–45.
Solution: The tool returns valid: None with an explicit "not defined, confirm with HR/Finance" message. It does not invent a rule, and the router logic treats "undefined" differently from "rejected".

5. Stale state between questions

Problem: Retrieved context and flags from a previous question could leak into the next one.
Solution: The router resets policy_context and rejection_explained on every new question.

How I evaluated it

  • Tool correctness: boundary checks on every rule (exactly 3 vs 4 CL days, 7 vs 21 days of notice, 15 vs 16 vs 45 vs 46 days for claims).
  • Routing accuracy: question pairs that differ only in "rule vs request" intent.
  • Grounding: checking policy answers against the source chapters and confirming the model declines when the context lacks the answer.
  • Trace review: inspecting runs in tracing to confirm the expected node sequence, especially the rejection detour.

10Results & Learnings

What the project delivers

  • An assistant that returns exact, repeatable answers for calculations and eligibility checks, because the logic lives in code.
  • Policy answers grounded in the handbook, with chapter references on tool results.
  • A fully inspectable flow: every question is traceable from router decision to final message.
  • A design that is cheap to run: local embeddings, a fast hosted model, and no LLM call at all for refusals.

What I learned

  • Use the LLM for language, not logic. The most reliable way to get correct numbers is to never ask the model to produce them.
  • Routing is a product decision. Splitting question types up front simplified every downstream prompt.
  • Explicit state beats clever prompts. A single boolean flag solved a loop problem that prompt wording could not guarantee.
  • "I don't know" is a feature. Modeling an undefined outcome separately from valid/invalid keeps the assistant trustworthy.
  • Observability pays for itself. LangSmith traces turned debugging from guesswork into reading a timeline.

11Future Improvements

Web or chat UI

Wrap the graph in a FastAPI backend with a Streamlit or React front end, or a Slack / Teams bot.

Conversation memory

Add a LangGraph checkpointer so follow-ups like "what about 6 days?" keep their context.

Personalized answers

Connect to employee records (joining date, grade, leave balance) so the assistant stops asking for inputs it could look up.

Better retrieval

Add a persistent vector DB, hybrid keyword + semantic search, reranking, and page / chapter citations in answers.

Automated evaluation

Build a LangSmith dataset and run regression evals on routing, tool selection and answer faithfulness for every change.

Access control & escalation

Role-based access, audit logs, and a hand-off to a human HR contact when the handbook has no answer.
